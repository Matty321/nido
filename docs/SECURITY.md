> Status: updated for 0.8.0 (localization: English base, with Italian, German, Spanish and French; Guest Tools 1.5.0, whose messages carry stable codes that the app shows in the user's language; installing Ollama accepts Guest Tools 1.4.0 or later; Developer ID signing and notarization of released builds; the fixes from the 2026-11 audit). Earlier: 0.7.5 (Debian build manifest checked and older builds rejected, two Ubuntu keys accepted for a key change, "Turn Off" offered to VMs created earlier); 0.7.4 (older signed lists rejected, apt-listchanges without network, local noise hidden in the log); 0.7.2 (Ubuntu signature verified, background requests turned off in existing VMs too); M3d (controlled network for VMs: relay on gvproxy, 0.6.0, per-domain permissions with Touch ID, notices, SNI check); M3b (macOS VMs from an IPSW, screen, terminal access) and M3c (Guest Tools, monitor over vsock, two-phase provisioning, Ollama, remote AI bridge, VM templates, guest robustness). Update it at each milestone (M1–M4) and before each release.

Labels such as M1 or M3c name Nido's development milestones: M1 the `nido` command (0.1.0); M2 the app (0.2.0); M3a suspend, snapshots, cloning, shared folders and Rosetta, and M3c the Guest Tools, the monitor, templates and the AI bridge (both 0.3.0); M3b macOS VMs (0.4.0); M3d the controlled network (0.5.0); M4 Developer ID signing and updates (0.8.0).

## Reporting a vulnerability
- Use the repository's **GitHub private vulnerability reporting** (Security → Report a vulnerability), once the repository is public.
- Don't open public issues for security problems.
- First response within 7 days; fix and advisory coordinated with the reporter.
- Supported versions: the latest release only.

## Threat model

### Assets
1. The user's files and data on the Mac (home folder, Keychain, SSH keys).
2. The Mac's integrity (no code execution outside the VM).
3. VM contents (disks, saved state, snapshots).
4. Secrets: private SSH keys, any disk encryption keys, the AI bridge's Hugging Face token (M3c).
5. Nido's supply chain (signed binaries, update feed).

### Adversaries
| Adversary | Capabilities | Goal |
|---|---|---|
| **Hostile VM** | root in the guest, virtio devices, network (Apple's NAT or the controlled network) | escape the VM, read the Mac's files, attack services listening on the Mac |
| **Tampered image** (ISO, IPSW, cloud image) | arbitrary content, man-in-the-middle on the download | run malicious code in the VM, deceive the user |
| **Unprivileged local user** | another account on the same Mac | read or change VM disks and configurations, take over a running VM |
| **Malicious `.nidovm` bundle** received from a third party | `config.json`, symlinks, arbitrary files | path traversal, overwriting files outside the bundle, dangerous configurations |
| **Compromised update feed** | altered HTTP response | install a malicious Nido |
| **Malicious CLI input** (scripts, automation) | arbitrary arguments | path traversal, command injection |
| **Guest hostile to the AI bridge** (M3c) | connections to `127.0.0.1:11435` in the guest, hence vsock 7701 to the Mac; arbitrary HTTP requests | read the Hugging Face token, spend the budget beyond the limits, reach hosts other than the router, crash the app |
| **Guest hostile to the monitor** (M3c) | arbitrary responses on vsock port 7700 | crash or hang the app with malformed, huge or slow JSON |
| **Guest hostile to the network** (M3d: an agent or a model in the VM) | root in the guest, arbitrary Ethernet frames to the relay, floods | exfiltrate data to destinations that aren't allowed (direct addresses, DNS, DoH/DoT, IPv6, ICMP, the Mac's services, shared CDNs), widen permissions without Touch ID, hide a block, stall the relay |

### Trust boundaries
```
[ Guest (untrusted) ] ──virtio──> [ Virtualization.framework (Apple) ] ──> [ nido process / app (trusted) ] ──> [ user file system ]
                                                      ▲
[ Network / download (untrusted) ] ──HTTPS + checksum─┘
[ .nidovm bundle (untrusted until validated) ] ──parser──> [ NidoCore ]
[ Guest (untrusted) ] ──vsock 7700 (monitor responses)──> [ app: GuestMonitorClient, read only ]
[ Guest (untrusted) ] ──vsock 7701 (AI bridge requests)──> [ app: AIBridgeProxy ] ──HTTPS + token──> [ router.huggingface.co → provider ]
[ app / nido ] ──SSH with the user's key, fixed commands──> [ Guest: nido-provision (root via sudo) ]
[ Guest (untrusted) ] ──Ethernet frames (controlled VM)──> [ EgressRelay relay: per-domain filter ] ──unixgram socket──> [ gvproxy: user-space NAT ] ──Mac sockets──> [ Internet ]
[ user processes on the Mac (out of scope for M3d) ] ──egress.json──> [ relay ]
```

## Controls

### Signing and distribution (M4)
- Hardened Runtime; Developer ID signature; notarization.
- Check: `codesign --verify --deep --strict --verbose=2 Nido.app` and `spctl -a -vv Nido.app`.
- Minimal entitlements:

| Entitlement | Where | Why | When |
|---|---|---|---|
| `com.apple.security.virtualization` | app, CLI | use Virtualization.framework | M1 |
| `com.apple.vm.networking` | app | bridged networking **only**; must be requested from Apple and justified; **not** used by the controlled network (M3d) | exploratory |
| Claim USB Accessory (Accessory Access) | app | USB passthrough, macOS 27 | v1 |
| `com.apple.security.network.client` | only if the app is sandboxed | image downloads, Sparkle | M4, if sandboxed |

- No `cs.disable-library-validation`, no `cs.allow-jit` (not needed without QEMU).
- App Sandbox: **no** (M2 decision). The app shares `~/Library/Application Support/Nido/VMs` with the CLI, which in a sandbox would need an App Group and therefore a Team ID. Compensating controls: Hardened Runtime on, a single entitlement (`com.apple.security.virtualization`), no external dependencies. `scripts/build-app.sh` checks at every build that the entitlement is exactly that one and that the `runtime` flag is present (`flags=0x10002(adhoc,runtime)` for an ad hoc build). Since 0.8.0, released builds are signed with a Developer ID and notarized: `scripts/release.sh` builds through `build-app.sh` with `NIDO_SIGN_IDENTITY` and submits the DMG with `notarytool`. Builds from source are signed ad hoc, unless `NIDO_SIGN_IDENTITY` names another identity.

### VM isolation
- Shared folders **only** as chosen by the user, **read only by default**; switching to read & write takes an explicit action per folder (the "Read only" switch in the app, `--rw` in the CLI).
- Shared folders (M3a): a single VirtioFS device (tag `nido`, `VZMultipleDirectoryShare`), mounted by the guest at `/mnt/nido/<name>` (`nosuid,nodev`, by a systemd unit, `nido-shares.service`, that is skipped when the device is missing: no fstab entry); since M3c the device is always there, with an empty share when there are no folders (so a folder can be added while the VM is running). The path must be absolute, must exist and must be a folder; it is resolved with `realpath` (symbolic links, `.`, `..`; a missing folder → "not found"; permission denied, a link loop or a file along the way → refused with the reason). `realpath` keeps other spellings of the same path, though: the prefixes `/.nofollow`, `/.resolve` and `/.vol` are refused, and the firmlink form of the data volume (`/System/Volumes/Data/X`) is mapped back to `/X` when it is the same folder. Then, by prefix: refused are `/System` and everything inside it (the home folder, the VMs and the cache live under `/System/Volumes/Data`), `/private` (where `/tmp`, `/var` and `/etc` really live) and `/dev`, and the root of any volume (`/` included; mount point according to `statfs`). These rules are what protect against volume-level aliases: in an APFS volume group, `st_dev` doesn't reliably tell the system volume from the data volume. Finally, by **identity** (`st_dev`, `st_ino`, walking up with `openat(fd, "..")`), never by string: refused are the home folder itself, `~/Library` or anything inside it, anything inside the VM root or the image cache (the app's or the CLI's, and always the default ones too), and a folder that contains one of these (e.g. `/Users`). A protected folder that doesn't exist yet is checked through its nearest existing folder. These checks fail closed: if an identity can't be computed, the folder is refused ("can’t check the folder"). Allowed by choice: folders under `/Volumes` (external disks, not their roots), `/Applications`, `/Users/Shared` and other users' readable home folders. The saved path is the resolved one. The rules run again at every start: a folder that disappeared, moved or became a link to a forbidden place is left out with a warning (CLI on stderr, app in the window's bar; control characters in paths shown as `\u{…}`) and the VM starts without it. The same goes for a folder whose path now resolves somewhere other than the path saved when it was added (case-insensitive comparison, after mapping `/System/Volumes/Data/X` back to `/X`): for example a folder in `/Users/Shared` or on an external disk that another user replaced with a symbolic link to an allowed folder of the victim, such as `~/Documents`. To get it back, remove it and add it again. Since M3c folders can also be changed **while the VM is running, from the app**: the session's `nido` device gets a new `share`, so removing a folder or switching back to read only takes effect at once; the CLI (`nido share add|remove`) refuses a VM running in the app ("the VM is running in Nido: change its folders in the app, or stop it first") and, for a VM started with `nido start`, the rule "only while the VM is stopped, under the bundle lock" still applies.
- **Folders and cloning (M3c)**: no shared folder by default; a clone and a new VM from a template **don't inherit** shared folders (nor write access): the new VM starts without them, and the user authorizes them again.
- **virtio-socket (M3c)**: every Linux VM has a `VZVirtioSocketDevice`. The app's monitor connects to port 7700 *of that VM* (no network, no IP: VMs are separate by construction); reads with a 2 s timeout, responses of at most 64 KiB, JSON decoded leniently, protocol version checked (`2.x`). The monitor is never needed to start a VM. The Mac listens on a single vsock port, 7701 for the AI bridge, and only for VMs started from the app (`nido start` registers nothing): at most 4 connections per VM, each handed to the bridge proxy, which answers `403` when the bridge is off. In the guest, the `nido-ai-bridge` shim listens only on `127.0.0.1:11435` (unit with `IPAddressDeny=any`, `IPAddressAllow=localhost`) and holds no token and no configuration.
- Rosetta (M3a): a second VirtioFS device (tag `rosetta`, `VZLinuxRosettaDirectoryShare`, mounted read only by the guest, `nosuid,nodev`, at `/media/rosetta` by `nido-rosetta.service`), only if the VM has Rosetta turned on and Rosetta is installed on the Mac; otherwise the VM starts without it, with a warning. The guest registers only x86_64 ELF binaries with binfmt_misc (standard magic/mask), with flag `F` and without `C`: a setuid x86_64 binary gains no privileges through Rosetta. Installing Rosetta on the Mac (`installRosetta`, a system installation) starts only from an explicit action: `nido rosetta install` with confirmation (or `--yes`) or the "Install Rosetta…" button with confirmation in the app; never on its own. Rosetta can be changed only while the VM is stopped, under the bundle lock.
- Shared clipboard: **no automatic channel** in M3a. The SPICE agent serves a graphical session, which genericcloud Linux VMs don't have (serial console only): no `VZSpiceAgentPortAttachment` attached (v1, with desktop images; off by default, can be turned on per VM). Instead, in the app's console: copying the selection only with ⌘C and pasting only with ⌘V, both explicit user gestures (paste rules under "The Nido app").
- No port of the Mac exposed by default. The only one Nido opens is a controlled VM's SSH forward, on `127.0.0.1` (see "Controlled network"); the old port forwarding (v1) no longer exists.
- No audio (neither output nor microphone: the genericcloud kernel has no `CONFIG_SOUND`; audio in v1) and no USB attached.
- **The Mac's memory (M3c)**: before a start (`nido start` and the app), `MemoryHeadroom` adds up the configured memory of Nido's running VMs, the footprint (`phys_footprint`) of other `com.apple.Virtualization.VirtualMachine` processes (Docker Desktop, other apps' VMs) and the memory of the VM about to start; above 75% of the Mac's RAM it warns ("the running VMs’ memory is over 75% of the Mac’s RAM: the guest may crash; …") without blocking. Reason: with the Mac's RAM overcommitted, macOS/Virtualization.framework lost pages of guest memory (M3c investigation), crashing the guest kernel. Processes are read with libproc (`proc_listallpids`, `proc_pidpath`, `proc_pid_rusage`, the list of open files to recognize those of Nido's VMs): read only, and only processes of the same user; no data leaves the Mac. On Macs with 16 GiB or less, the memory offered at creation is smaller (Debian Base 2 GiB, AI profile 4 GiB), and can always be changed.
- The Linux configuration has: disk, read-only seed, network (Apple's NAT or, since M3d, the controlled network's relay with its `gvproxy`), entropy, balloon, serial console (M1); since M3a the `nido` VirtioFS device (shared folders) and, only if configured, the `rosetta` one; since M3c also a virtio-socket device. Nothing else.

### Saved state, snapshots, suspend and cloning (M3a)
- **The saved state contains the guest's memory** (`state.vzvmsave`: RAM, so also keys, passwords and data open in the VM). It exists only inside the bundle: `state.vzvmsave` for a suspended VM, `snapshots/<uuid>/state.vzvmsave` for a snapshot taken while the VM was running; never in `$TMPDIR` or anywhere else. It is written straight into the bundle by `saveMachineStateTo`, checked at once with `PrivateFile` (regular file, a single link, owned by the user) and set to `0600` (directories `0700`); for snapshots it is cloned into a `0700` `.partial` folder. Virtualization.framework protects it with a key tied to this Mac: it can be restored only here.
- **A state resumes only on the machine it was saved with**: `suspendedConfigHash` (SHA-256 of CPUs, memory, MAC, the folders actually attached and whether Rosetta was actually attached) must match the hash of the machine that starts; otherwise the state is **discarded** (file removed, hash cleared) and the VM cold-boots with a warning. The same goes for an invalid file (link, FIFO, empty, owned by another user) or for a state that Virtualization.framework rejects. The hash is cleared before every restore and before the files are touched: an interruption never leaves a resumable state on a different disk.
- **Interruption-proof snapshots and restore** (details in `docs/BUNDLE-FORMAT.md`, "Snapshots"): creation in `snapshots/.<uuid>.partial/`, renamed only when the work is done; restore follows "invalidate first, commit last" (`.new` copies next to the files, originals moved to `.old`, a `.restore-<tag>.commit` marker, hash written last); the next operation under the lock (`recoverBeforeUse`: start, snapshot, restore, clone) completes or rolls back an interrupted restore and **refuses to proceed** if `.restore-*` files remain (never deleted automatically: they could be the only copy of a disk). Restore and delete only while the VM is stopped (lock available); otherwise refused without touching anything. Free space checked beforehand (2 GiB margin).
- **Suspend from the CLI (signal protocol)**: `nido stop --suspend` sends `SIGUSR1` only to the process that holds the lock with owner `cli`, that is a `nido start` (never to the app or to itself, as with `SIGTERM` for `nido stop`; never to a maintenance command, which holds the lock as `cli-op` and must not be interrupted halfway: refused at once with "an operation … is in progress"). `nido start` ignores `SIGUSR1` from the first instant (an early signal doesn't kill it) and receives it through a dispatch source installed before the VM starts; a signal that arrives between taking the lock and installing that source is lost, and `nido stop --suspend` stops waiting after 5 minutes, saying that the VM doesn't appear to be suspended. If it can't suspend, it answers with the reason in `<bundle>/.suspend-result` (`PrivateFile`, `0600`, at most 4 KiB, read without following links and removed by `nido stop --suspend`); otherwise it suspends, releases the lock and exits.
- **Cloning with a new identity**: only while the VM is stopped, under the source's lock, built in a `.cloning-` folder and renamed with `RENAME_EXCL`. The clone gets a new `id`, MAC, `VZGenericMachineIdentifier`, `instance-id` and cloud-init host name (and therefore new SSH host keys: the clone's `user-data` explicitly sets `ssh_deletekeys: true`, so cloud-init deletes the keys copied from the source before generating new ones), and regenerates `/etc/machine-id` once at first boot; it gets no `known_hosts`, snapshots or saved state (the source's RAM is not copied). It does copy Rosetta; **since M3c it doesn't copy shared folders** (the new VM starts without them, and the user authorizes them again).
- **Rosetta**: installing it on the Mac never starts on its own, neither when a VM starts nor when Rosetta is turned on for one: only `nido rosetta install` (with confirmation) or "Install Rosetta…" (with confirmation).

### Guest Tools, monitor, provisioning and AI bridge (M3c)
- **Read-only vsock**: the monitor uses only `GET /api/status` on the VM's vsock port 7700 (one `VZVirtioSocketDevice` per VM: no IP, no network, VMs separate by construction). No management command goes over vsock: installations, retries, Ollama, models and logs go over SSH. The app's client reads with a 2 s timeout and at most 64 KiB, one request at a time, I/O never on the main thread; a huge or non-numeric `Content-Length`, truncated JSON, missing or mistyped fields and a future protocol version don't bring down the panel ("invalid response", "Guest Tools version not recognized"). The monitor sets no thresholds of its own: it shows the guest's verdicts (CPU > 85%, RAM > 85%, disk > 90%).
- **Unprivileged Guest Tools**: `nido-guest-tools.service` and `nido-ai-bridge.service` run with `DynamicUser=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `NoNewPrivileges=yes`, `Restart=on-failure` and, since 1.3.0, with no capabilities (`CapabilityBoundingSet=`), private `/tmp` and `/dev`, kernel, modules, kernel log, clock, host name and cgroups protected, no namespaces and no writable executable memory, native system calls only and only the address families they need (`AF_UNIX AF_VSOCK` for the monitor, `AF_UNIX AF_INET AF_VSOCK` for the shim; the host name is protected only in the shim, because the monitor reports it); the monitor reads `/proc`, `statvfs("/")` and, read only (`ReadOnlyPaths=-/var/lib/nido-provision`), the provisioning state (`state.json`, 0644, no secrets). The monitor listens **only** on `AF_VSOCK` 7700, never on TCP: no network port, not even on loopback. The one documented exception: the bridge shim (below). The Guest Tools live in `/opt/nido-guest-tools/`, use only the distribution's Python 3 and its standard library (no pip dependencies), and don't touch the user's files in the guest (e.g. `/home/nido/monitor.py`, port 8080 of its API).
- **Management over SSH with the user's key**: `GuestSSH` uses the public key saved in the config (`sshPublicKeyPath`) and the matching private key only as a path for `ssh` (see "Data"), the bundle's `known_hosts`, `BatchMode=yes`, `RemoteCommand=none`, `RequestTTY=no`, `ControlMaster=no` and `ControlPath=none` (they take precedence over a `Host *` in `~/.ssh/config`, which is still read for `IdentityAgent`), and per-command timeouts. The commands are **constant** (`GuestCommand`): `sudo -n /opt/nido-guest-tools/bin/nido-provision <step>` with fixed or validated arguments (model name, `--force`, `--keep-models|--remove-models`), each argument quoted for the remote shell; no user text is put into a shell line. The Guest Tools package and the chat arrive over stdin. `sudo -n` works because Nido's seed gives the `nido` user `NOPASSWD:ALL` (as before M3c); no password in the guest. This is a deliberate choice, not a hidden assumption: the VM belongs to the user and `nido` is their account (as in Debian's cloud images); Nido itself runs only `nido-provision`, with constant arguments, through `sudo`. Whoever has the VM's SSH key is its administrator (see "Residual risks").
- **Seed without secrets**: the `user-data` holds only the public key, the packages, the Guest Tools files (base64, `root:root`), the units and the panic settings; no password, token or private key. A VM without a profile has a `user-data` byte-for-byte identical to the one before M3c (fixture test), apart from the `systemd-timesyncd` file that every new Linux VM has since M3d (see "Controlled network"). cloud-init runs once per instance: existing VMs get the Guest Tools and the panic settings only through an explicit action over SSH, never through a cloud-init reset. The seed of a VM created from a template contains only the identity.
- **Ollama on the guest's loopback**: `ollama.service` (user `ollama`, `OLLAMA_HOST=127.0.0.1:11434`, `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `RestrictSUIDSGID` and other restrictions) is installed and enabled only by `nido-provision ollama-install` (phase 2); the app's chat reaches the local API inside the SSH session (`curl --noproxy '*' --max-time 900` with constant arguments, messages over stdin). No port opened on the Mac, no change to the guest's firewall. No GPU acceleration: Ollama in the VM uses the CPU. The conversation stays in the app's memory (no file, no log, no state restoration); it leaves the process only through **Copy**, by the user's choice, to the macOS clipboard. Markdown in replies is rendered with native SwiftUI views (never HTML or a WebView); only `http`/`https` addresses with a host, without user or password (`https://apple.com@evil.com` would lead to evil.com) and not pointing to the Mac itself (`localhost`, loopback, `0.0.0.0`), stay links, opened in the browser and checked again on click (`OpenURLAction`); every other scheme (`file:`, `javascript:`, `mailto:`, `data:`, other apps' schemes) is plain text. A link's visible text can still name a site other than its destination, as on any web page.
- **Shared folders (the user's rule)**: "No shared folder by default. Explicit, limited and revocable access." No folder at creation, in the Debian Base / AI Starter profiles, in provisioning or in VM templates; **a clone and "New VM from template" don't inherit them** (nor write access); removing a folder or switching back to read only **while the VM is running in the app** takes effect at once (the session's `nido` device gets a new `share`). Provisioning and Guest Tools never use shared folders. A VM with `guestMountsSharedFolders` false (created before M3a) doesn't see folders added while it runs until it runs the one-time command: the app says so.
- **VM templates**: a template (`isTemplate`) can't be started or cloned by mistake (`VMSession`, `nido start`, `nido clone` and the app refuse it); "New VM from template" uses M3a's cloning with a new identity (id, MAC, machine identifier, `instance-id`, host name, `/etc/machine-id`, SSH host keys with `ssh_deletekeys`) and **doesn't inherit** shared folders, the AI bridge policy or a pending phase 2.
- **Remote AI bridge (Hugging Face Inference Providers)**:
  - **Off by default** for every VM; the first time it is turned on (per VM), the privacy notice appears: with the bridge, **text leaves the Mac** for Hugging Face and for the provider that serves the model (subject to their terms). An "AI bridge active" indicator in the VM window and in the library; Local mode (Ollama) is always available.
  - **Token only in the Mac's Keychain** (generic password, service `Nido Hugging Face`, account `default`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`), entered in Settings (secure field, never shown again; the typed value is forgotten when the user leaves the section). **Never** in the bundle, the seed, logs, error messages or toward the guest: `HFToken` isn't `Codable` and always prints as `HFToken(redacted)`; the proxy strips every authentication header from the guest and adds its own; `SecretFilter` cuts a response before any complete copy of the token (streaming included), and a non-streaming response that contains it becomes a `502`.
  - **Only `https://router.huggingface.co/v1/`** (allowlist: base URL fixed in the code, `POST /chat/completions` and `GET /models`; every other path → `404`, even with the bridge off; redirects refused; ephemeral session with no cache, cookies or credentials on disk; 120 s timeout).
  - **Per-VM limits** (in the config, `aiBridge`): allowed models (exact ids from the catalog, only the policy and provider suffixes accepted), tokens per day (default 200,000; from the response's `usage`; when streaming, the proxy adds `stream_options.include_usage`; without `usage`, a conservative estimate multiplied by `n` is charged), requests per minute (20), `max_tokens` enforced (4,096, also when missing or not positive), at most 2 concurrent requests; budget used up → `429` until local midnight. Bridge off → `403`, token missing or revoked → `401`, always in OpenAI error format and without any network call.
  - **Log without content**: `ai-bridge.log` (0600, one JSON line per call: time, model, provider, input and output tokens, estimate yes/no, outcome, duration; rotated at 1 MiB) and `ai-bridge-usage.json` (0600); never prompts, replies, headers or tokens. If `ai-bridge.log` can't be opened, the bridge doesn't connect (no call without a log) and the AI section says the bridge isn't available in this session.
  - **Defenses against a hostile guest**: HTTP/1.1 requests only, headers ≤ 16 KiB, body ≤ 1 MiB (refused from the declared `Content-Length` before it is read; `Transfer-Encoding` refused), read within 10 s (`408`), JSON in **strict UTF-8** only (no BOM, NUL, UTF-16/32) and **nesting of at most 32**, checked before any recursive parser and again during decoding (nested JSON used to crash the app: fixed and covered by tests), body rewritten without losing numbers, router responses read on demand (no unbounded buffer; at most 8 MiB for a non-streaming response); **at most 4 connections per VM** on the Mac (beyond that: closed at once) and 4 in the guest's shim (beyond that: `503`); waiting on the guest's sockets doesn't hold threads (read/write `DispatchSource` with timeouts), so a guest with stalled connections doesn't block the app.
  - **Lifecycle**: the Mac listens on vsock 7701 only while the session's machine exists; when it stops, is suspended (saved state) or fails, `AIBridgeHost.shutdown()` removes the listener, cancels the requests still being served (the call to the router is canceled at once, even while the response is being read) and refuses new connections. A resumed VM has a new session and a new bridge.
  - **Router errors without account data**: a Hugging Face `4xx`/`5xx` keeps its status code, but the guest receives only a fixed explanation (`upstream_unauthorized`, `upstream_payment_required`, `upstream_not_found`, `upstream_rate_limited`, `upstream_timeout`, `upstream_unavailable`, `upstream_invalid_request`); the router's body, which can name the account or the organization, isn't read.
  - **The guest's shim** `nido-ai-bridge` is the Guest Tools' only TCP listener: only `127.0.0.1:11435` (unit with `IPAddressDeny=any`, `IPAddressAllow=localhost`, `DynamicUser`); it copies bytes to vsock (CID 2, port 7701) and holds no token and no configuration. Any process in the guest can use it (like Ollama on loopback): policy and limits are per VM, not per process.
  - The bridge works only for VMs started from the app (the Mac listens on vsock 7701 only there); with `nido start`, the shim answers `502 bridge_unavailable`.
- **Guest robustness** (M3c investigation into the crashes): with the Mac's RAM overcommitted, macOS/Virtualization.framework lost pages of guest memory, and the guest panicked and hung with its CPUs at 100%, without visible messages. For VMs created with the Guest Tools: `console=tty0 console=hvc0` (panics reach `console.log`), `kernel.panic = 10` and `kernel.panic_on_oops = 1` (automatic reboot within 10 s); for existing VMs, only through an explicit action over SSH. Before a start (`nido start` and the app, also from the library), the warning when the memory of running VMs exceeds 75% of the Mac's RAM (see "VM isolation"), without blocking. Linux VM disks with `cachingMode = .cached` and `synchronizationMode = .full` (the user's decision of 2026-10-25, measurements in `docs/DISK-CACHING.md`): every guest flush is still an `F_FULLFSYNC` on the Mac.

### Controlled network (M3d)
The relay and its filter arrived in 0.5.0, on top of vmnet; since 0.6.0 the NAT behind them is done by `gvproxy`, and the vmnet approach (which needed the Mac's IP forwarding) was abandoned.

**What it defends against**
- The adversary is the **guest**: the agent or model in the VM, with root, trying to get data out without permission (direct addresses, DNS to other servers, DoH/DoT, IPv6, ICMP, the Mac's services, frames with forged addresses, packet floods).
- **Tampering from the Mac is out of scope.** Touch ID protects Nido's commands, but a user process on the Mac can write `egress.json` (or `config.json`) directly, and the relay applies it. Defending against the Mac's processes is out of scope.
- Nido sees the VM as a whole: it doesn't know which program in the guest opens a connection.

**Data path**
- Since 0.6.0 new VMs start on the controlled network again, and it works **without the Mac's IP forwarding** (`net.inet.ip.forwarding` stays 0; Nido no longer reads or changes it). The NAT is done by `gvproxy`, one process per VM, in user space: it opens connections to the Internet with the Mac's ordinary sockets. VMs on Apple's NAT are chosen in the settings.
- A controlled VM has no `VZNATNetworkDeviceAttachment`. Its network interface is a `VZFileHandleNetworkDeviceAttachment` on a Unix datagram socketpair. On the other side, the relay (`EgressRelay`, in the process that runs the VM: the app or `nido start`) passes Ethernet frames between the VM and `gvproxy` (`GvproxyUplink`, Unix `SOCK_DGRAM` socket, one frame per datagram) and decides frame by frame (`EgressFilter`), **in both directions, before the frame reaches `gvproxy` and before it reaches the VM**. `gvproxy` does DHCP (the VM always has `192.168.127.2`, gateway `192.168.127.1`, subnet `192.168.127.0/24`), DNS and NAT; the relay passes or drops, without terminating TCP.
- **No extra permission**: `com.apple.security.virtualization` is enough. `com.apple.vm.networking` isn't used (with an ad hoc signature AMFI kills the process), and vmnet is no longer used. `gvproxy` needs no entitlements and runs with the Hardened Runtime.
- **From the VM outward, only this passes:**
  - DNS over UDP to the gateway. The relay answers NXDOMAIN (negative TTL 3 s) for names not on the list and for names with characters other than letters, digits, `-` and `_`; it forwards questions for allowed names with the same bytes (standard question: exactly one, class IN, at most one OPT without data; EDNS size reduced to 1232);
  - TCP and UDP to an address the relay learned from a DNS response for an allowed domain, while still valid;
  - DHCP and ARP from the VM itself to the gateway, and SSH responses to connections opened by the Mac.
- **Paths that don't go through the network interface** (residual risk: the relay doesn't see them and they aren't in `egress.log`): the AI bridge (vsock 7701, when on); writable shared folders (a folder the Mac syncs, for example with iCloud or Dropbox, carries out whatever the VM writes there); the SSH session to the Mac. For the latter, Nido turns forwarding off: every ssh from Nido to a controlled VM (`nido ssh` included) and every background command has `ClearAllForwardings=yes`, `Tunnel=no` and `PermitRemoteOpen=none`, before the user's options, so a `RemoteForward` in the user's ssh configuration doesn't give the guest a way out through the Mac's ssh client.
- **Always dropped** (with a log entry): addresses never resolved (`denyUnknown`); ports 53 and 853 to other servers (`dnsBypass`, so no bypassed DNS or DoT; DoH to an address not learned is an unknown address); ICMP and other protocols (`denyProto`); IPv6 (`ipv6`); multicast and broadcast (`broadcast`); fragments, IP options (DHCP included) and malformed frames (`malformed`); source MAC or IPv4 other than the VM's (`spoofed`); anything going to the gateway or to the vmnet subnet other than DHCP, the relay's DNS and SSH (`hostSubnet`, checked by subnet and not by "private" ranges: it also holds for networks with public numbers).
- **From outside toward the VM**, only frames for its MAC arrive: DHCP and ARP from the gateway, SSH from the Mac to port 22, packets of open allowed flows, and DNS responses that match a forwarded question (txid, port and question).
- **What the relay learns**: only from the resolver's responses to the questions it forwarded, the A records under the name asked or its CNAME chain. Never from the VM's frames, never from unsolicited or broken responses. The TTL reaches the guest reduced to the smallest in the chain and to at most 60 s; the relay keeps the address for at least 10 minutes (`DNSLearner.minTTL`, at most one hour), because programs such as apt reuse the addresses they resolved at the start for a long time. Removing the domain forgets its addresses at once, and every new connection checks the list again: the longer lifetime applies only to domains that are still allowed.
- **CNAME targets**: an allowed domain's DNS is fully trusted. A name that an allowed domain's response points to with a CNAME can be asked for directly while the response is valid (only types A, AAAA, CNAME and HTTPS; at most 1024 aliases), and the log shows it as `domain via target`.
- **Open flows**: they last until FIN/RST plus 10 s, until an hour without traffic for TCP, 180 s for UDP, or until their domain is removed.
- **Speed** (measured with the first, vmnet-based relay of 0.5.0): about 16 MB/s from the Internet, the line's limit, with 16–17% of one core in the Release build.

**`gvproxy`: a pinned third party, SSH forward on `127.0.0.1`**
- **A third-party binary, the only exception to the "no external dependencies" rule** (the author's decision of 2026-11-02). `gvproxy` from `containers/gvisor-tap-vsock` is written in Go, with a TCP stack (gVisor). Version (0.9.0), URL, size and SHA-256 are in `Resources/gvproxy/release.json`; `scripts/fetch-gvproxy.sh` downloads it only at build time and checks size and hash; **never downloaded at run time**. It is re-signed with Nido's identity (identifier: the app's bundle identifier followed by `.gvproxy`, Hardened Runtime) and placed in the app's `Contents/Helpers/gvproxy`; before every start, Nido checks that the file is regular (not a link) and that its signature satisfies a code requirement (`GvproxyBinary.requirement`): under a Developer ID signature, Apple's anchor, that identifier and Nido's own Team ID, so a binary signed by anyone else, or ad hoc, is refused; in an ad hoc build, the identifier only. No hash is checked at run time: a process on the Mac that can replace the helper can also rewrite `egress.json` (tampering from the Mac: out of scope). Updates are an explicit choice (`release.json` changes). Apache-2.0 license: `LICENSE` and `NOTICE` (with the embedded Go modules and their licenses) are in the bundle in `Resources/gvproxy/`.
- **The filter decides before `gvproxy`**: the VM talks only to the relay. Services that `gvproxy` offers on the gateway and that the filter keeps closed (tested against a live `gvproxy` and covered by filter tests): the HTTP API on the gateway, port 80, with which the VM could make `gvproxy` open listening ports on the Mac; and the address `192.168.127.254`, which `gvproxy` translates to the Mac's `127.0.0.1` and which would therefore give the VM every local service. The filter drops every destination inside `192.168.127.0/24` except the gateway for DNS and DHCP (`hostSubnet`). In addition, `gvproxy` always starts with an API token (random at every start, `0600`, never used by Nido: without the filter the API would answer 401), without `-listen` (no control API), without `-debug`, `-pcap`, `-services` or `-forward-*`: the process's only TCP port is the SSH forward.
- **SSH forward**: `127.0.0.1:<port>` → `192.168.127.2:22`, written in `gvproxy`'s configuration (`stack.forwards`; the static lease ties the VM's MAC to `192.168.127.2`). It listens only on `127.0.0.1`: another process of the user can connect to the port, but it needs the private key (the same was true of the address on `bridge100` with vmnet). The port changes at every start and is stored in `ssh-forward.json` in the bundle (`0600`, with PID and start time); `nido ssh`, `nido ip` and the app's SSH commands read it from there. Forwarded connections reach the VM from the gateway's address, the form that `sshFromHost` recognizes. No VM port other than 22 can be reached from the Mac.
- **Socket folder**: per VM, `<TMPDIR>/nido-gv/<8 digits of the id>/` (`0700`), with `gvproxy`'s socket, the relay's socket, `gvproxy.pid`, configuration, token and `owner.lock`. Paths stay under 104 bytes even with long VM and library names.
- **Orphan processes**: `gvproxy` doesn't die on its own with the process that started it (tested: after a `kill -9` of the parent it is reparented to PID 1 and keeps listening). Whoever starts it holds a `flock` on `owner.lock`; when the app opens, at the beginning of every `nido start` (any VM, NAT ones included) and at every start of `gvproxy` (app and CLI), `sweepOrphans` stops the `gvproxy` processes whose lock is free, checking the process's name and start time before signaling it, and frees socket and port. So after a `kill -9` of Nido a `gvproxy` can stay alive **until the app next opens or the next `nido start`** (not forever, but not "a few seconds" either); with no useful network, since nothing talks to its socket any more, but with that VM's SSH port still open on `127.0.0.1`.
- **What a firewall on the Mac sees**: allowed traffic goes out as the user's `gvproxy` process, not as Nido (Little Snitch and similar tools ask about `gvproxy`).
- **Measurements** (M-series Mac, macOS 26, Debian 13 VM with 2 vCPUs, `gvproxy` 0.9.0 without the filter, before it was integrated): `apt update` from scratch, 28.5 MB in 32 s with 0.93 s of `gvproxy` CPU time; a large 400 MiB download at 12.75 MB/s (the same line gives 11.74 MB/s directly from the Mac, so the line is the limit) with about 59% of one core (37–82%). With vmnet it was 16–17% of one core for about 16 MB/s: `gvproxy` costs more CPU, but stays under one core at line speed. With the relay and the filter in front, the live test of 2026-11-03 downloaded Ollama (the Mac's archive) and a small model without problems; the large-download measurement wasn't repeated with the filter.

**Failing closed**
- If `gvproxy` doesn't start (binary missing, invalid signature, no free SSH port, no answer in time), the VM starts **without a network**: the relay keeps the socketpair and drops every frame, and Nido says so ("Controlled network not started (…): the VM starts without a network."). If `gvproxy` dies while the VM is running, the relay drops every frame, writes the loss to the log and warns ("Controlled network interrupted…"); `nido ssh` gives a clear error instead of a timeout (the forward file no longer points to a live `gvproxy`). Never Apple's NAT for a controlled VM, Linux or macOS. Only an invalid MAC or a socketpair that can't be created prevents the start.
- In the app the relay starts off the main actor and is closed even when the session fails to be created; with `nido start`, also when the configuration fails validation. Closing doesn't block the main actor: it happens on the relay's queue, after the last events have been handed to the log (`nido start` waits for it before exiting).
- **Domain list** in `egress.json` in the bundle (`0600`, atomic writes under `.egress.lock`, at most 256 KiB and 512 entries). A malformed or oversized file, a link or a file not owned by the user isn't used: a running VM keeps the last valid list (never a wider one), and the commands refuse to change it and point to `nido net reset <vm>` or "Reset to Base List…". Nido never rewrites it on its own.
- **Live changes**: the relay rereads the list when it changes (watching the bundle folder, plus a check every 2 s). An added domain applies within a few seconds; a removed one cuts the open flows to it at once. The guest is told: for every cut TCP connection that has already received data, the relay sends it a reset right away (at the sequence number the guest expects), and for 120 s answers with a reset every segment the guest sends on it; so a program waiting for data fails at once instead of hanging until its TCP timeout. The relay works in bounded rounds, so a guest that floods it delays neither a removal nor stopping the VM.
- **Names**: ASCII only; only `A`–`Z` are lowercased (no Unicode case folding: for example U+212A doesn't become `k`). `example.com` covers only itself; `*.example.com` covers `example.com` and every subdomain of it.

**Which VMs are controlled**
- Linux and macOS VMs created since 0.6.0 are controlled by default (`controlledNetwork: true`; 0.5.1 started them on Apple's NAT because vmnet required IP forwarding). Linux starts with the base list `EgressPolicy.base` (or `ubuntuBase`) in `egress.json` from the first boot. Existing VMs stay as they are: a `config.json` without the field (schemas 1–4) counts as false, even after it has been rewritten.
- The field brings the schema to 5, which earlier versions of Nido refuse (`unsupportedSchema`, a check present since schema 1): an old version can't start a controlled VM on the NAT, nor rewrite its config without the field.
- New macOS VMs (`MacInstaller`) are controlled with the macOS base list (`EgressPolicy.macOSBase`, exact names, no wildcards): `albert.apple.com` (device activation), `gdmf.apple.com` and `mesu.apple.com` (update catalogs), `swscan.apple.com` and `swdist.apple.com` (what `softwareupdate --list` needs: without either one it fails, verified live on 2026-11-03), `time.apple.com` (date and time). Every name is in a real VM's log **and** in Apple's article "Use Apple products on enterprise networks" (support.apple.com/101555, read on 2026-11-02). Left out, even though blocked: `xp.apple.com` (it was on the first list; `softwareupdate` works without it and it sends more data than it receives, probably analytics), the servers updates are downloaded from (`updates.cdn-apple.com`, `updates-http.cdn-apple.com`: allow them by hand to update the VM), the App Store and iTunes, iCloud and CloudKit, push notifications, Maps and location, `ocsp2.apple.com` and `ocsp.digicert.com`. So an Apple ID, iCloud and the App Store don't work until the user allows their servers. Existing macOS VMs stay on the NAT until the user turns on the controlled network in the settings (the list then starts from the macOS base list if `egress.json` is missing).

**Base list** (verified on 2026-10-29, exact names only)
- Debian: `deb.debian.org` (packages and security updates). Ubuntu (`EgressPolicy.ubuntuBase`, chosen from `VMConfig.distribution`): `archive.ubuntu.com` and `security.ubuntu.com` (arm64 archive of 26.04), `ports.ubuntu.com` (arm64 archive of 24.04), exact names only. Ubuntu's background requests stay out: `motd.ubuntu.com`, `api.snapcraft.io`, `changelogs.ubuntu.com`, `contracts.canonical.com`, `entropy.ubuntu.com` and apt's `_http._tcp` SRV queries (verified on 2026-11-02 on throwaway 26.04 and 24.04 VMs). Since 0.7.1 the seed of a new Ubuntu VM turns them off (`UbuntuQuiet`, once per instance): it masks snapd, motd-news, the Ubuntu Pro timers, apt news and pollinate, sets `ENABLED=0` in `/etc/default/motd-news` and `Prompt=never` in `/etc/update-manager/release-upgrades` with `sed` (never replacing a conffile), and writes `Acquire::EnableSrvRecords "false";` to a new file in `apt.conf.d` (since 0.7.2 in every new Linux VM, Debian included: `GuestAptSRV`). Since 0.7.4 every new Linux VM also has `/etc/apt/listchanges.conf.d/nido-no-network.conf` with `no_network=true` (`GuestAptListChanges`): Debian's cloud image strips the packages' changelogs, and `apt-listchanges.timer` (every hour, until it succeeds the first time) asks `metadata.ftp-master.debian.org` for them with `apt changelog`, which is refused; without the network the database is built from local files and the timer turns itself off (verified on 2026-11-10 on a throwaway Debian 13 VM: with the option no requests, without it yes). For VMs created earlier, Settings › Guest Tools › Background requests · Turn Off writes the same settings over SSH (`GuestCommand.quietBackground`, fixed script, only on request and while the VM is running; tested live on 24.04). Since 0.7.5 the Network tab of a Linux VM created earlier offers it ("Turn Off" / "Not Now"): the offer appears when `config.json` has no `backgroundRequestsOff` and the seed's `user-data` doesn't write `GuestAptListChanges.path`; the answer stays in the config (`true` after Turn Off or at creation, `false` after Not Now) and carries over to clones and templates. No command runs without the click: Nido only reads files in the bundle. Verified on 2026-11-09 on throwaway 26.04 and 24.04 VMs: none of these names in the log, a clean `apt update`. Ubuntu VMs created earlier stay as they are. In all of them: `registry.ollama.ai` and Ollama's R2 bucket `dd20bb891979d25aebc8bec07b2b3bbc.r2.cloudflarestorage.com` (`ollama pull`), `time.cloudflare.com` (clock).
- Deliberately excluded: GitHub, because the Mac downloads Ollama's archive (below) and such an open site would be a channel for getting data out; Debian's NTP pool, because those are volunteers' addresses that the relay would open on every port.
- **What it doesn't guarantee, not even with the base list alone**: the controlled network stops accidental and naive traffic, **not** a root guest determined to get out. The base list's names sit on CDNs shared by many customers (Fastly, Cloudflare): an address learned for them also serves other sites, reachable with the Host header on port 80, with a split ClientHello (the name outside the first segment) or with QUIC; and a learned address stays usable on every port for at least 10 minutes.
- The cloud-init seed of new VMs configures `systemd-timesyncd` with `NTP=time.cloudflare.com` and an empty `FallbackNTP=` (`/etc/systemd/timesyncd.conf.d/nido.conf`).

**Permissions with Touch ID or the Mac password** (LocalAuthentication, `.deviceOwnerAuthentication`; no permission widens without it)

| Action | Where | Authentication |
|---|---|---|
| Add a domain | `nido net allow`, "Allow" in the notice or in the log, "Add…" in the settings | yes; a broad wildcard (at most two labels, known public suffixes, `amazonaws.com`) first asks for a confirmation with the same warning, both in the app and with `nido net allow` ("Add Anyway" in the app, `[y/N]` in the terminal), and only then for Touch ID |
| Remove a domain | `nido net deny`, "Remove" | no: the list narrows |
| Reset to the base list (`EgressPolicy.macOSBase` for macOS) | `nido net reset` | always, after a confirmation in the terminal |
| Reset to the base list ("Reset to Base List…") | the app's settings | only if it widens the list (a broken file counts as widening), decided under the file lock on the file as it is |
| Turn on the controlled network | settings, VM stopped | no: going from the NAT to the list narrows |
| Turn it off (back to the NAT) | settings, VM stopped | yes |

- From the terminal, `allow` and `reset` refuse without an interactive terminal; if authentication fails or is canceled, the list doesn't change.
- "Allow" appears only for a block that names an exact domain (never an address, a wildcard, a name like `_https._tcp…` or a cut connection), checked again when the button is pressed. It adds exactly that name.
- A running VM changes its list live; the controlled network switch only while the VM is stopped (the config is written under the bundle lock).

**Notices and noise**
- **A block always goes to the log.** With the app open, the blocks of every VM (also those started with `nido start`: the app reads the logs every 2 s) become notifications with the VM, the destination and the port. With the app closed, `nido start` writes a line to stderr, and the app picks up the blocks from the log at its next launch (one cursor per VM; on the very first launch it starts from the end).
- **Merging**: one notification per VM, destination and port every 10 s, with the count; at most 10 destinations per VM per minute get a notification of their own, the others go into an "N other destinations" notice. The counts always add up every notified block. On stderr, one line per destination every 10 s plus "blocked N more times…".
- **Log only, no notification or counter** (startup noise, `EgressLogEntry.isLocalNoise`; since 0.7.4 `nido start` doesn't print it, the Network tab and `nido net log` don't show it, and `nido net log` says how many lines it hid, `--all` to see them; it stays in `egress.log`): `broadcast` (multicast included), IPv6 without an address or to `ff00::/8` and `fe80::/10`, `malformed` without an address, and every block to the link-local broadcast `169.254.255.255`, whatever the outcome (`hostSubnet`, `denyUnknown`, …: they are all dropped anyway). Every line that names a domain is notified, and so is every link-local unicast address (for example `169.254.169.254`). Cuts (`cut`) aren't notified: the user asked for them by removing the domain.
- **Notifications denied**: the Network tab of the VM window shows a counter of unseen blocks and says so.
- **Relay limits against floods**: the same block (type, protocol, address, port) once every 10 s, with repeats counted in the next line; at most 20 blocks per second, then an "N more blocks not shown" summary. Noise that isn't notified (listed above) has a budget of its own (10 per second) and a count of its own in the summary (`lostNoise`, never notified): a flood of all-different multicast or broadcast doesn't turn real blocks into a summary; they stay lines with their destination. Flow ends and cuts have their own budget (100 per second) and, in the filter, beyond it they are deferred, never lost; the hand-off to the log, though (at most 1024 pending events per type), can lose some with a slow consumer: they are counted as unlogged flows (`lostFlows`) in a summary.

**Log without content**
- `egress.log` (blocks, cuts and summaries) and `egress-flows.log` (allowed connections, merged per destination every 10 s, plus a line every 60 s for long connections), both `0600`, links refused, rotated at 1 MiB in separate files: a burst of connections doesn't erase the blocks. JSON lines with time, domain, address, port, protocol, bytes out and in, outcome.
- Never packet contents (tested with a marker payload). The VM's domains are written only there, on `nido start`'s stderr and in notifications; printed text goes through `ConsoleSanitizer.echoable` (no control, bidi or zero-width characters).
- If the log can't be opened (for example, a link put in its place), the VM still has a network: no log, but blocks stay blocks. Nido says so: "Network log unavailable: blocking stays on, but blocks aren’t logged or reported." (a `nido start` warning and in the VM window), and the app sends a notification for that VM, once per app launch, when there is a link or a non-regular file in place of the log. If the log is a normal file that the relay refuses (another owner, a hard link), only the warning in the window and the one on stderr remain.

**TLS name check (SNI)**
- For TCP connections to port 443 of an allowed address, the relay reads, once, the first segment with data that the guest sends. If it is a TLS ClientHello with a name (`server_name`) that the list doesn't allow, neither as a domain nor as a still-valid CNAME target of an allowed domain, the segment is dropped, the guest receives a reset, the connection is cut in both directions and the log records `denyDomain` with that name (the app offers "Allow", with Touch ID). It guards against shared-CDN mistakes (an address of `deb.debian.org` used for another site on the same CDN) and against naive domain fronting. Later segments are never read or held back; other ports and other protocols are untouched. It is enough for the name to be allowed by any entry in the list, not necessarily the one the address was learned for.
- **Stated limits** (this is not a defense against a hostile guest):
  - Without a name, or with the name outside the first segment (a ClientHello split or padded on purpose), the connection goes through: the domain learned from DNS applies, as if the name were missing. The same for non-TLS data on port 443, with no extra lines in the log.
  - The name can end up outside the first segment even without malice: a browser's ClientHello is large (the post-quantum key adds about 1.8 KB), and Chrome and NSS-based programs shuffle the order of extensions, so the name can land after the first segment and pass unchecked. Command-line tools built on OpenSSL or GnuTLS (`curl`, `apt`) put the name in the first segment and are checked.
  - After a refusal, the relay keeps the connection marked for about 10 s: a new connection that reuses the same pair of addresses and ports within that time is dropped silently (no reset, no new log line) until the mark expires. No reset goes to the server: its half-open connection times out on its own.
  - **ECH** (Encrypted Client Hello): the cleartext name is the provider's public one, so these connections are blocked unless that name is on the list.
  - **QUIC/HTTP3 on UDP 443** isn't checked: the relay lets it through like any UDP flow to an address learned for an allowed domain.
  - IPv6 doesn't leave the VM, so there is nothing to check.

**macOS VMs** (verified on 2026-10-29 on `macos-prova`, macOS 26.6.2)
- The relay is the same as for Linux VMs (`MacConfigurationBuilder` uses the same network device, `LinuxConfigurationBuilder.networkDevice`); if `gvproxy` doesn't start, the VM stays without a network, never on the NAT. The IPSW installation of a controlled VM also runs on the relay, which is closed when the installation ends (blocks during that time go only to the log in the installation folder, without notices).
- Verified from the Mac, from the relay's log: an address from DHCP (tested with vmnet; with `gvproxy` the path is the same and the address is `192.168.127.2`), DNS only through the relay (NXDOMAIN for names not on the list), an allowed HTTPS connection (`albert.apple.com`, added while the VM was running) and the blocked Apple names. Inside the guest, on 2026-11-03 with `gvproxy`: Setup Assistant through to the desktop (Apple ID skipped), `softwareupdate --list` and the clock. Not verified: App Store and Apple ID.
- **Empty list** (what new macOS VMs got before 0.6.0; since then they start with the macOS base list, see "Which VMs are controlled"; a list can still be emptied by hand): macOS reaches no Apple service (activation, push notifications, iCloud, App Store, updates) until the user adds the names. Every blocked name produces a notice (merged as for Linux), so a macOS VM with an empty list gives a few notices at every start.
- **A way through Setup Assistant** (history, from before 0.6.0: the macOS base list includes `albert.apple.com`, and with it Setup Assistant reaches the desktop, verified on 2026-11-03): if a VM stops at activation, add `albert.apple.com` (plus the names the VM's network log shows), with Touch ID, or turn off the controlled network for Setup Assistant and turn it back on afterwards. A new installation with an empty list hasn't been tested all the way through.
- **Apple names macOS asks for at startup**, for information only: of these, only `albert.apple.com` is on a default list (the macOS base list, `EgressPolicy.macOSBase`); the others are NOT on any. `albert.apple.com` (activation), `init.push.apple.com`, `push.apple.com`, `1-courier.push.apple.com`, `1-courier.sandbox.push.apple.com` (push notifications), `appleid.apple.com`, `ocsp2.apple.com` and `ocsp.digicert.com` (certificate revocation), plus `_dns.resolver.arpa` and the reverse lookup of its own address. In this test macOS asked neither for `captive.apple.com` nor for the `softwareupdate` or App Store servers; they too, being off the list, get NXDOMAIN.

**Ollama comes from the Mac** (Guest Tools 1.4.0)
- The guest never downloads Ollama's archive. Nido downloads it on the Mac (`OllamaArchiveStore`, `~/Library/Caches/Nido/ollama`, `0700`/`0600`) from the URL pinned in `release.json`, checks its size and SHA-256 before publishing it to the cache (redirects only `https` to `github.com` or `*.githubusercontent.com`, without credentials, port 443), and sends it into the VM on the stdin of `nido-provision ollama-install --archive-stdin` over SSH, copying it from the file in blocks (never memory-mapped). The guest writes exactly `size` bytes and checks the SHA-256 again before extracting it.
- Before downloading, Nido checks that the VM's Guest Tools receive the archive on stdin (1.4.0 or later, `/opt/nido-guest-tools/VERSION`): with older Guest Tools it downloads nothing and asks for them to be updated. Two concurrent installations share a single download; `.part` files left by an interrupted download (regular files, never links, untouched for an hour) are removed the next time the cache is used.
- **The cache doesn't clean itself**: when the pinned Ollama version changes, the old archive stays in `~/Library/Caches/Nido/ollama`. Delete it by hand (the whole folder can go: Nido creates it again and downloads again at the next installation).

**Cloning and snapshots**
- A clone, or a VM from a template, inherits `controlledNetwork` and the source's list (rewritten from the valid content, never copied by name; unreadable = empty list). The logs stay with the source.
- A snapshot doesn't contain `egress.json`, on purpose: a restore keeps the current list and never brings back a domain removed after the snapshot (that would be a widening without Touch ID).
- The saved state of a controlled VM doesn't resume on the NAT, nor the other way around: `controlledNetwork` goes into `stateHash()` when it is true.

### macOS VMs (M3b)
- **The IPSW belongs to the user and Nido only reads it**: it downloads nothing, doesn't change it, doesn't move it, doesn't copy it (the file stays where the user put it; in the project folder, `/ipsw/` is in `.gitignore`). Before creating any file in the VM root, Nido inspects it with `VZMacOSRestoreImage` and honors Apple's checks: `isSupported`, `mostFeaturefulSupportedConfiguration` not nil, `hardwareModel.isSupported`, CPUs and memory at least at the image's minimums. A file that isn't an IPSW, is truncated, or holds a macOS version newer than the Mac's (for example the 27 beta on a Mac with macOS 26) is refused with a message that says why. Right before the installation starts, the IPSW is checked again (`lstat`: regular file, not a symbolic link).
- **No signature of its own on the IPSW**: the image's authenticity is what Virtualization.framework and Apple's installer verify; Nido has no list of checksums for IPSWs.
- **The bundle's macOS files at `0600`** (folder `0700`), all created with `PrivateFile` or protected right after creation: `auxiliary-storage.img`, `hardware-model.bin`, `machine-id.bin`, `authorized_key.pub`, as well as `disk.img` and `config.json`. `VMBundle.verifyInnerFiles(for: .macos)` checks the set of macOS files (safe paths, no symbolic links) before any file reaches Virtualization.
- **Installation in `.creating-<UUID>`**: the installation takes place in a `0700` folder in the root, with a `BundleLock` held for its whole duration, and becomes `<name>.nidovm` only when the work is done (`renamex_np` with `RENAME_EXCL`). Before the rename, `disk.img` and `auxiliary-storage.img` are synced with `F_FULLFSYNC`, then the folder and the root. If the installation is canceled or fails, the folder is removed at once; after a crash it is swept the next time the library opens, when nothing inside it has changed for more than 2 minutes and the lock is free (with the lock held by another process it is never removed). The folder never shows up in the list of VMs.
- **Cloning a macOS VM**: only while the VM is stopped and under the source's lock. The clone gets a new `VZMacMachineIdentifier`, a new MAC and a new `id` (hence a new `HostKeyAlias=nido-<id>` and no `known_hosts`); disk, auxiliary storage and hardware model are copies, `authorized_key.pub` is copied if present, shared folders start empty. **Identity left in the guest**: the guest's SSH host keys and computer name are the original's. Nido can't change them from outside, so it prints (CLI) and shows (Clone sheet) the steps to take once in the copy's Terminal: `sudo rm /etc/ssh/ssh_host_* && sudo ssh-keygen -A`, `sudo scutil --set ComputerName/LocalHostName/HostName`. The clone started from the 26.6.2 IPSW booted with the new identifier; the effects on an already configured machine (Keychain, activation, identity-bound services) haven't been verified.
- **No shared clipboard and no microphone**: macOS VMs have no clipboard agent and no audio input device (only an output to the Mac). `clipboardSharing` is always false.
- **Only basic features for macOS (R4)**: Guest Tools, the vsock monitor, provisioning, Ollama, the AI bridge and VM templates are **Linux only**. A macOS VM has no vsock device, serial port, Rosetta or AI bridge (`VMSession.attachAIBridge` refuses it in any case), and `nido template save` and "Save as Template" are refused.
- **No password asked for or stored by Nido**: the user creates the guest's account in macOS Setup Assistant; Nido knows only the user name (`sshUser`, for `nido ssh`) and a **public** key.
- **"Type in VM"** ("Terminal Access" panel): types a **constant** command into the guest's Terminal (the text is fixed in the code, with only the public key inside it), as synthetic keystrokes on the VM's view.
  - The key comes from `authorized_key.pub`, read with `PrivateFile` (`O_NOFOLLOW`, a regular file with a single link, owned by the user, `0600`) and capped at **16 KiB**; a symbolic link or a larger file is refused, and the button stays disabled.
  - Before typing, the key is validated: one line of `[A-Za-z0-9+/=@._ -]`, at least two fields, type `ssh-`, `ecdsa-` or `sk-`, at most 8192 bytes. A character that the keyboard can't produce stops everything **before** the first keystroke.
  - **Layout limit**: keystrokes are computed with **this Mac's** keyboard layout (`UCKeyTranslate`); if the guest's layout differs, the command arrives altered. The panel says so under the command (the user can type it by hand or copy it).
  - **Nido doesn't press Return**: the user sees the command in Terminal and runs it themselves.
  - **While typing, the user's keys are blocked** (`blocksUserKeys`: keyDown, keyUp, flagsChanged and real ⌘ combinations are dropped; the mouse isn't). Before every event Nido checks that the VM is running; if it isn't, or if the window closes, it stops and warns that the command may have been typed only partly. A modifier (Shift, Option) counts as pressed from just before its key-down is sent, and stops counting only once the key-up has gone out: if typing is interrupted (error, cancellation, even right after an event already delivered), Nido sends the key-up of every modifier still counted as pressed (one too many is harmless). Covered by tests with a fake sender; **not verified live**.
- **`nido ssh` on macOS**: before opening the session, it probes the guest's port 22 **once** (non-blocking `connect()`, 2 s wait, no data sent, no shell); if the connection is refused, it says to turn on Remote Login instead of "Connection refused". The `sshSucceeded` flag in the config (optional, excluded from `stateHash()`) becomes `true` after the first `nido ssh` that reached the guest (ssh ended normally with a code other than 255; never with `-V`, `-G`, `-Q`, `-O`); it serves only to avoid reopening the panel on its own and grants no permission. Until then, `nido ssh` starts `/usr/bin/ssh` as a child (fixed argv, `posix_spawn`) instead of replacing itself with it.
- **Closing the window**: for a macOS VM it asks nothing and the VM keeps running; reopening the window brings the screen back to the same session. Verified with a fake session (`-NidoFakeSessions`) by the UI test `MacWindowTests.testTerminalAccessPanelAndClosingKeepsTheVMRunning` (closing without questions, card still "Running", "Open" brings the window back); not verified live with a real macOS VM.

### Data
- VM root `~/Library/Application Support/Nido/VMs` and cache `~/Library/Caches/Nido/images`: directories `0700`, files `0600`.
- Optional disk encryption with a key in the Keychain (v1; mechanism to be designed and verified).
- No password in a guest created by Nido: access only with an SSH public key (`ssh_pwauth: false`, `lock_passwd: true`, `disable_root: true`).
- Private SSH keys are never read or copied: Nido reads only the `.pub` file the user points to. Since M3c, the app's background SSH (Guest Tools, Ollama, models) passes `/usr/bin/ssh` the **path** of the matching private key (`-i <key without .pub>`, `IdentitiesOnly=yes`, `BatchMode=yes`): `ssh` opens it, never Nido; a passphrase goes only through the SSH agent (without an agent: a clear error and an offer to open Terminal with `nido ssh`).
- Per-VM `known_hosts` inside the bundle (`StrictHostKeyChecking=accept-new`), with the key tied to the VM's identity and not to its address (`HostKeyAlias=nido-<VM id>`): if the address or, with `gvproxy`, the forward port on `127.0.0.1` changes at every start, the VM must present the same key (tested: stop and start again on another port, no warning or prompt). Entries written earlier (by IP) are no longer used: the first connection after the update records the key under the alias. The path is passed to ssh in quotes inside the argument (`-o UserKnownHostsFile="<path>"`), because ssh splits the value on spaces (the default root contains "Application Support") and expands `%`; paths containing `"`, `\`, `%` or a newline are refused. Always `GlobalKnownHostsFile=/dev/null`, `ForwardAgent=no`, `ForwardX11=no`; since M3d, for a VM on the controlled network and for every background command, also `ClearAllForwardings=yes`, `Tunnel=no` and `PermitRemoteOpen=none` (see "Controlled network").
- Logs: no secrets; home folder paths may be shortened to `~`.

### Image downloads
- `https` only; allowlisted hosts (`cloud.debian.org`, `cloud-images.ubuntu.com`). Both the URL of the checksum list (`SHA512SUMS` for Debian, `SHA256SUMS` for Ubuntu) and the image's initial URL must pass `DownloadPolicy.validate`.
- Checksum list: redirects are validated with the same allowlist too (no redirect to other hosts).
- Image: `cloud.debian.org` serves it through mirrors, so the image's redirects (and only the image's) may point to any host, as long as it is `https`, without user/password and with no port or port 443 (`DownloadPolicy.validateMirrorRedirect`). Integrity is still guaranteed by the SHA-512 read from the `SHA512SUMS` downloaded under the strict rule.
- Redirects are checked at every hop and on the final URL (a chain `cloud.debian.org` → `https` mirror → `http` mirror is refused).
- Ephemeral HTTP session (`URLSessionConfiguration.ephemeral`, `urlCache = nil`, `reloadIgnoringLocalCacheData`): no HTTP cache, cookies or credentials on disk. Timeouts: 60 s without data per request, 6 hours for the whole download.
- Streaming: the image is written in blocks straight into a `.part` file inside the cache (created with `O_CREAT|O_EXCL|O_NOFOLLOW`, `0600`), never in `$TMPDIR`, and the SHA-512 is computed while writing.
- Size limits: every catalog image has a maximum (`debian-13`: 8 GiB); a larger `Content-Length` is refused before writing, and the transfer is stopped as soon as the bytes received exceed the limit (the `.part` is deleted). `SHA512SUMS` is limited to 1 MiB.
- **List signature (Ubuntu, since 0.7.2)**: `SHA256SUMS.gpg` (same host, 64 KiB limit) is verified before the list is read, both at download time and in `nido image check`, by `OpenPGPSignature`, in Swift and without `gpg`: an OpenPGP v4 signature of a binary document, RSA PKCS#1 v1.5 with SHA-256 or SHA-512 (Security.framework), ASCII armor or binary; other algorithms, unknown critical subpackets, expired signatures and a different issuer fingerprint are refused. The accepted keys are built into the code (`UbuntuCloudImageKey.keys`; today only one, "UEC Image Automatic Signing Key <cdimage@ubuntu.com>", RSA 4096, fingerprint `D2EB 4462 6FDD C30B 513D 5BB7 1A5D 6C4C 7DB8 7C81`); a test recomputes the fingerprint from the bytes and verifies the real 26.04 signature. Signature missing or invalid: no image downloaded, no comparison. **Key change** (since 0.7.4): a signature that is well-formed but made by another key is refused with a message that names the issuer (fingerprint or key ID) and asks for an updated Nido, instead of a generic "invalid"; the issuer read from the signature is used only for the message, never for trust. Procedure for updating the key (since 0.7.5 in two releases, so that on the day of the change nobody is left without images): get the new public key from `keyserver.ubuntu.com` and compare its fingerprint with the one Ubuntu publishes (verification pages of `ubuntu.com` and `cloud-images.ubuntu.com`) over a channel other than the keyserver; in the first release, add it to `UbuntuCloudImageKey.keys` next to the current one (a new `packetBody`/`fingerprint`, with the test that recomputes the fingerprint), so both are accepted; once Ubuntu signs only with the new one, a second release removes the old one and updates `OpenPGPSignatureTests`'s real `SHA256SUMS`/`.gpg` fixtures; record it in this document and in the CHANGELOG. A signature that names its issuer is tried only with the key of that fingerprint; one without an issuer, with each key. **Older lists refused** (since 0.7.4): the signature has no expiry, so whoever controls the transport (compromised TLS or a mirror) could serve an old but valid list-and-signature pair to hold the cache on an earlier build. `ImageStore` saves the creation time of the last accepted signature for each image in `<file>.signed` in the cache (Unix seconds) and refuses a signature created earlier ("it may be an old copy served again"), before downloading the image; it compares only signature times, never the Mac's clock. The file is written 0600 and atomically; if the write fails, the valid list is used anyway (the protection doesn't advance), and an unreadable file counts as the first time. If the refusal keeps happening (for example, a catalog that moves to a folder with an older list), the message points to `nido image reset <id>` (since 0.7.6), which, after a confirmation, deletes the image's `<file>.signed` and `<file>.build`: the next list counts as the first time, and the image in the cache stays. Residual limit: the first list seen on a Mac (empty cache or deleted file) has no reference; a process on the Mac that deletes or damages `<file>.signed` removes the protection (tampering from the Mac: out of scope). No signature can make Nido accept an image not signed by Ubuntu.
- Checksum verification (SHA-512 for Debian, SHA-256 for Ubuntu: `CloudImage.checksum`) **before** any use; on failure the file is deleted. The file next to the cached image is named `.sha512` or `.sha256` and must have the right length.
- **qcow2 images (Ubuntu)**: Ubuntu publishes arm64 cloud images only in qcow2. `Qcow2Image` (Swift, without `qemu-img`) converts them into the VM's raw, sparse disk at creation. It accepts only qcow2 v2/v3 without a backing file, without encryption, without an external data file, without extended L2 entries, with zlib compression; it refuses the "corrupt" bit and every unknown incompatible feature. Every offset and length of the L1/L2 tables and of the clusters is checked against the file size, the virtual disk is limited to 4 TiB, the source file is opened without following links, and the destination is created with `O_EXCL|O_NOFOLLOW` in `0600` and removed on any error. Before writing, since 0.7.1, it refuses tables that use an L2 table or a data cluster (compressed or not) twice, and those that describe more than 64 times the file's bytes (at least 256 MiB): a small file can't become a disk full of written data. Ubuntu's cloud images are around 4 times. This also applies to `nido create --image-file` with the user's own qcow2.
- No download without explicit confirmation (a dialog in the app, a prompt or `--yes` in the CLI).
- **New builds** (since 0.7.0): a valid copy in the cache is used without the network, so it stays that copy until the user asks. `nido image check` and "Check for a New Build" in the Download step download only the checksum list (same rules: allowlist, size limit, ephemeral session) and compare the published digest with the one in the file next to the image, without reading the image. Never automatically. `nido image update` and Download after the check download the image again with all the rules above and replace it only after verification; VMs already created don't change.
- Temporary files in the same directory as the cache, atomic move, cleanup on error.
- Local images (`--image-file`): a "not verified" warning.

### Downloads in the guest (M3c)
- **Never without the user's choice**: phase 1 (cloud-init) installs only the distribution's essential packages from the Debian mirrors configured in the image (`package_update: true`, never `package_upgrade`); Ollama and models come only from phase 2, that is from "Install Ollama after first boot" (off by default) in the wizard or from the actions in the AI section, never from cloud-init or automatically. At most one model is downloaded automatically (the one chosen in the wizard).
- **Ollama at a pinned version with a checksum**: `guest/linux/ollama/release.json` pins the version (`0.40.10`), the URL of the official GitHub release (`https`) and the SHA-256 (from the release asset and from `sha256sum.txt`, verified on 2026-10-24). Up to Guest Tools 1.3.0, `nido-provision` downloaded into `/var/lib/nido-provision/tmp/<file>.part` (not into `/tmp`; resuming with `Range` only if the response is consistent; redirects only `https`). Since Guest Tools 1.4.0 (M3d) the guest no longer downloads: it receives the already verified archive from the Mac on stdin (`--archive-stdin`, see "Controlled network"), writes it there and verifies its SHA-256 (different → file deleted, step failed), extracts it and checks `ollama --version` in a working folder, and only then moves the tree with a rename into `/usr/local/lib/nido-ollama/<version>/`. No remote installer is run (`curl | sh`). An Ollama not installed by Nido (another `/usr/local/bin/ollama` or `ollama.service`, even masked) is never replaced or removed.
- **Models**: identifier validated with the same conservative regular expression in Swift and in Python (at most 128 bytes, no leading `-` and no shell characters), downloaded through Ollama's local API (`POST /api/pull`), never overwritten without confirmation; before the download, a free-space check and a warning (never a block) if the VM's RAM is below 1.2 × the model's size. Model integrity is what Ollama guarantees (the registry's layer digests): Nido doesn't add its own.

### `.nidovm` bundle
- VM names validated: `^[A-Za-z0-9][A-Za-z0-9._-]{0,62}$`, no `..`, case-insensitive comparison.
- Bundle path resolved and confined to the root; bundle symlinks refused.
- `config.json` with `schemaVersion`; future versions refused; CPUs and memory validated against Virtualization.framework's limits.
- Exclusive lock (`flock`) to prevent two concurrent runs; an orphaned lock after a crash doesn't block.
- The lock has an **owner**: whoever holds it writes `"<pid> <owner>\n"`, with `owner` = `cli` (`nido start`) or `app` (the Nido app). The app and the CLI use the same lock and see each other's VMs (`nido list`: "running (app)"; the app's card: "Running (Terminal)").
- Inner files: before the VM configuration is built (`VMSession`, `LinuxConfigurationBuilder`), `config.json`, `disk.img`, `nvram.efi`, `machine-id.bin` and `seed.iso` are checked with `lstat`: a regular file (not a symlink), owned by the current user, a single hard link; otherwise "unsafe path".
- `config.json` is read with `O_NOFOLLOW` and must be a regular file of at most 64 KiB; `nido list` uses the same read and doesn't follow symlinks.
- Importing third-party bundles (future): no symlinks inside, no files outside the expected set. A received bundle's `config.json` isn't trusted: the import will have to **clear `sharedFolders` and `rosetta`** (a bundle prepared by someone else could point to Mac folders to share, even with write access) and leave the choice of adding them to the user; today bundles are created only locally.

### The `nido` CLI
- Strict validation of names, paths and sizes.
- No shell: `Process`/`execv` with argument arrays and executables with absolute paths (`/usr/bin/hdiutil`, `/usr/bin/ssh`).
- `nido delete` asks for confirmation (or `--yes`) and refuses running VMs. While holding the lock, the bundle is renamed atomically to `<root>/.<name>.deleting-<uuid>` (ignored by `list` and `open`); then the lock is released and the "tombstone" deleted recursively (symlinks refused). A concurrent `start` can't start a half-deleted VM.
- `nido ip` and `nido ssh` work only for running VMs (bundle lock held); from the DHCP store, only literal IPv4 addresses in canonical form (`inet_pton`) and unexpired leases are accepted.
- `--ssh-key` must end in `.pub`: otherwise the file is refused before it is opened. The `.pub` is opened with `O_NOFOLLOW|O_NONBLOCK`: if it is a symlink (e.g. `foo.pub -> id_ed25519`, which would open the private key), it is refused as unreadable, as are FIFOs and non-regular files; the content checks remain (no private keys, at most 16 KiB).
- Files Nido writes inside the bundle (`.lock`, `console.log`, `console.log.1`, `known_hosts`): opened with `O_NOFOLLOW|O_NONBLOCK`, then `fstat`: a regular file, a single hard link, owned by the current user, otherwise "unsafe path" (a hard link to `~/.zshrc` or a FIFO never receives data and doesn't block the app); then mode `0600`. A released lock empties the file before unlocking: no old pid stays written.
- `console.log` is limited to 16 MiB with a single rotated generation (`console.log.1`, replaced by rename): at most 32 MiB on disk per VM, the latest bytes always in `console.log`. This holds for the app and for `nido start` (the CLI also goes through the same `SerialConsole`, write-only for the guest: the same set of devices).
- `nido start --console` no longer hands the terminal to the guest: it prints the output cleaned by `ConsoleSanitizer` (all ESC/CSI/OSC/DCS/APC/PM/SOS sequences dropped, C1 controls and C0 controls except TAB, LF and CR; invalid UTF-8 dropped; bounded state, sequences over 4096 bytes abandoned). No OSC 52 clipboard, titles, reports or sequences toward the host's terminal emulator.
- `nido start` stops the VM in an orderly way on `SIGHUP` too (like `SIGINT`/`SIGTERM`) and ignores `SIGPIPE`.
- `nido stop` sends `SIGTERM` only to a `nido` process (lock owner `cli`) and never to the very process that asks. A VM open in the app (owner `app`) is **refused** with "is open in the Nido app": the signal would reach the app and close all its VMs. The app, on the other hand, can stop a VM started from Terminal ("Stop" on the card sends `SIGTERM` to the `nido start` that holds it).
- `nido stop --suspend` follows the same rules with `SIGUSR1` (the `nido start` process ignores it until it can suspend, then suspends and exits).

### The Nido app (M2)
- **No App Sandbox**, Hardened Runtime, only `com.apple.security.virtualization` (see "Signing and distribution"). The VM runs in the app's process (Virtualization.framework's XPC process belongs to Apple); the app takes `BundleLock(owner: .app)` before creating the session and releases it only when the machine has surely stopped.
- Closing the window or quitting with VMs running asks for confirmation, then an orderly stop (30 s, then forced); a stop already in progress is waited for, never interrupted. If the forced stop fails, the lock stays held until the machine is found stopped, so neither the app nor `nido start` starts the same disk twice.
- **DEBUG-only launch arguments**: `-NidoRoot <absolute path>` (VM root for the UI tests), `-NidoImageFile <absolute path>` (a local image instead of the download, without a checksum), `-NidoFakeSessions` (VM windows without a VM, for the UI tests), `-NidoFakeStates "name=state,…"` (fake VMs started at launch in a fixed state: `starting`, `running`, `paused`, `error`) `-NidoWizardFixture <state>` (the wizard opened in a fixed state), these two for `ScreenshotTests`' screenshots; since M3c, `-NidoFakeAIRouter` (AI bridge with a fake router and an in-memory token: no network, never the Keychain) and `-NidoFakeGuest "name=scenario,…"` (fake monitor and Ollama for a fake VM, for the S13–S15 screenshots); since M3d, `-NidoNotifications allowed|denied` (in-memory notifications and an authenticator that refuses: no system prompt, no real Touch ID; with any test root the app uses in-memory notifications and throwaway preferences); in DEBUG, `-AppleInterfaceStyle Dark|Light` also forces the appearance. They are read only inside `#if DEBUG` / `isDebug`: in Release the app always uses `NidoPaths.defaultRoot()`, the catalog with checksums and real sessions. Relative paths or unknown values make the launch fail with a message (no fallback value); `-NidoFakeSessions`, `-NidoFakeStates`, `-NidoWizardFixture`, `-NidoFakeAIRouter`, `-NidoFakeGuest` and `-NidoNotifications` without `-NidoRoot` are refused before the root is even prepared, because fake VMs take real locks.
- Unit test hosts (`XCTestConfigurationFilePath`, checked only in DEBUG builds) neither create nor list the real VM root.
- Quit confirmed: from that moment no VM can start (a VM started within the 30 s of the shutdown would be killed); with the wizard downloading or creating, quitting asks ("VM creation in progress") and stops the download (partial file removed) or waits for the creation to end, never a half-made bundle. A VM in error whose machine may still be running (failed pause, resume or forced stop) can be stopped from the window, the library, the settings and on quit.
- Deleting from the app: the lock carries the owner `app` (not `cli`), so neither `nido stop` nor the app itself can send `SIGTERM` to the app during a deletion.
- **Serial console (S07)**: the guest's output is **untrusted**. The terminal parser is bounded: scrollback ≤ 5000 lines, fixed grid, CSI sequences ≤ 256 bytes (beyond that: abandoned), OSC/DCS counted but never stored or executed (no title, OSC 52 clipboard, OSC 8 links, palette, bell), incomplete UTF-8 ≤ 3 bytes, numeric parameters limited to 9999 and to at most 16. The **only** automatic replies to the guest are DSR 5n (status OK) and DSR 6n (cursor position): they contain only numbers, no host data, and go out only while the VM is running (R-M2-35).
- Host → guest input **only from the user's keyboard events** in the VM window and from an explicit paste (⌘V); the other ⌘ shortcuts stay with the app. Pasting is limited to 32 KiB (half the input queue, so a maximum paste with the bracketed paste markers always fits whole) and cleaned: newlines become Return, control characters (ESC included) are dropped, so pasted text can't inject sequences or close a bracketed paste early. Input queue 64 KiB, read stream 64 blocks of ≤ 256 KiB; `console.log` with the rules above (0600, private file, 16 MiB + one rotation).
- **Download in the wizard (S03)**: the Download step shows the origin (`cloud.debian.org`), file, maximum size and SHA-512 verification **before** any request; nothing goes on the network until the user presses "Download". Cancel stops the download and the cache removes the `.part`; a wrong checksum → a readable error, file deleted, "Try Again". All of `ImageStore`'s rules apply (a download shared between concurrent creations, which proceeds with the first caller's confirmation). Publishing to the cache: first the `.sha512` file, then the image, both by atomic rename; checking the cache never deletes an entry it finds invalid or incomplete (another process could be publishing it at that moment): a mismatch downloads again and replaces both files. No image is ever used unless its SHA-512 matches.
- The preselected key is `~/.ssh/id_ed25519.pub` (with an absolute `$HOME`, as a shell does); only `.pub` files with a valid public key are accepted, never private keys.
- VM settings (S08): saving takes the bundle lock (owner `app`) for the whole atomic write of `config.json`, so the configuration of a running VM can't be changed (neither from the app nor from the CLI).

### Privileged helpers
- To be avoided. If needed (e.g. bridged networking), `SMAppService` + XPC with verification of the caller's signature, minimal surface, documented here before implementation.

### Updates (M4)
- Sparkle with EdDSA signatures; feed and packages over HTTPS only; the EdDSA private key never in the repository.

## Residual risks (M1)
- **Mirror redirects**: the image's redirects can point to any `https` host, even a literal IP or a host on the local network. Integrity is still guaranteed by the SHA-512, but the request does reach that host.
- **Debian build manifest (since 0.7.5)**: next to the Debian image, Debian publishes a JSON manifest (`debian-13-genericcloud-arm64.json`, listed in `SHA512SUMS`) with the build version (`20261103-2651`) and the SHA-512 of every format. `ImageStore` downloads it (same host, 1 MiB limit), both at download time and in `nido image check`, and refuses, before the image: a manifest other than the one the list names, one that gives the `raw` image a checksum other than the list's or uploads from another build, a build older than the last one accepted, the same build with another checksum. The last accepted build is in `<file>.build` in the cache ("<version> <sha512>", 0600, atomic; a failed write or unreadable file: as for `.signed`). If the refusal keeps happening, the message points to `nido image reset <id>`; `nido image check` shows the accepted build (since 0.7.6). This is not a signature: whoever controls TLS or the server can rewrite the list and the manifest together; it only stops inconsistent files and a return to an older build. Verified on 2026-11-10 on the real files (`nido image check debian-13`).
- **Debian's `SHA512SUMS` trusted only through TLS**: Debian's cloud images publish no signature of the list (in `trixie/latest/` and in dated folders such as `trixie/20261103-2651/` there are only `SHA512SUMS` and the JSON manifests, verified on 2026-11-10; the page `cloud.debian.org/images/cloud/` says that only the old OpenStack images have `SHA512SUMS.sign` and asks for contributions to sign the current ones). To be reconsidered if Debian starts signing them. Ubuntu's `SHA256SUMS` is signed and verified since 0.7.2.
- **DHCP client-id spoofing**: another guest on the same shared NAT network can announce the VM's MAC/client-id and make `nido ip`/`nido ssh` resolve its own address before the first SSH connection; with `accept-new`, its host key would be accepted. Host key pinning (read from the console at first boot) is planned for M2.
- ~~**Console**: `console.log` without a limit and escape sequences forwarded by `nido start --console`~~: fixed in M2 (16 MiB limit with rotation, `ConsoleSanitizer`).
- **TOCTOU on inner files**: between the `lstat` check and Virtualization.framework opening the file, a process of the same user could replace a file; the bundle is `0700`, so that already requires access as the same user.

## Residual risks (M2)
- **Test builds not hardened**: the project sets `ENABLE_HARDENED_RUNTIME = YES` in Debug and Release, but both configurations sign ad hoc (only `build-app.sh` passes a named identity, from `NIDO_SIGN_IDENTITY`), Xcode drops the Hardened Runtime for ad hoc signatures, and hosted unit tests can't be injected into a hardened ad hoc app (library validation without a Team ID). So the builds produced by `xcodebuild test` run without the Hardened Runtime. `build-app.sh` builds and checks **Debug and Release** (a single entitlement, Hardened Runtime requested explicitly from `codesign`), and released builds come from it (`scripts/release.sh`, with the Developer ID).
- **Debug artifact**: it contains the DEBUG arguments (root, local image, fake sessions); Release doesn't, and Release is also the one `build-app.sh` checks.
- **Window while acquiring the lock**: between `flock` and writing the `"<pid> <owner>"` line there is a sub-millisecond window in which the file is empty (or holds the previous line of a process that terminated abnormally): a concurrent `holder` sees pid -1 (treated as "running, pid unknown", never signaled).
- **Ad hoc signature of builds from source**: released builds are signed with a Developer ID and notarized (since 0.8.0); a build from source (`build-app.sh` without `NIDO_SIGN_IDENTITY`) is ad hoc, so Gatekeeper can't attribute it to a developer, and its `gvproxy` check covers the identifier only (see "Controlled network").
- **Close confirmation**: it relies on interposing the window delegate in front of SwiftUI's, with a KVO observer that puts it back in front if SwiftUI changes it (e.g. after full screen). An internal change in SwiftUI could bypass it; quitting the app (⌘Q) stays protected by `applicationShouldTerminate`. Covered by the UI tests.
- **`SIGTERM` to the lock's pid**: "Stop" on a VM started from Terminal (and `nido stop`) signals the pid written in the `.lock` file, without checking that it really is a `nido` process. The bundle is `0700`: writing a different pid already requires a process of the same user.
- **DEBUG arguments**: anyone running a Debug build can point it to another root or to an unverified image; distributed builds are Release.
- **Console**: a guest can still fill the scrollback (5000 lines) or show misleading text in the console; in the app's window, Unicode format characters (Cf: bidi, zero width) are shown as U+FFFD (since M3a), while `--console` passes them to the terminal as they are (escape sequences, no). Parsing happens on the main actor (under heavy output the interface can slow down; the view redraws only when the buffer changes).
- ~~**Console keyboard**: no `NSTextInputClient`~~: fixed in M3a (dead keys and input methods compose; selected text is copied with ⌘C).
- **No sandbox**: a vulnerability in the app (e.g. in the console parser) would have the user's permissions; the surface exposed to the guest is the console parser and Virtualization.framework.

## Residual risks (M3a)
- **Shared folders, TOCTOU**: the path is verified (by identity) at start and must still resolve to the path saved when it was added (a symbolic link put in its place before the start excludes it), but Virtualization.framework reopens it by path right afterwards; someone who can write to the folder that contains it and replaces it with a symbolic link exactly in that window could expose another folder. The folder's identity (`st_dev`, `st_ino`) isn't saved: a different real folder created at the same path (rename and new folder) is shared in its place, but it contains only what its creator put there.
- **Read & write folders**: the guest can change and delete everything the folder contains (including symbolic links it creates itself, interpreted by the Mac only if a Mac program follows them). Turning off "Read only" is an explicit choice per folder.
- **Other ways to reach the same data**: another mount of the same files (local Time Machine snapshots under `/Volumes`, an SMB loopback mount of the home folder, a mounted disk image) has different identities and isn't recognized as the home folder or a Nido folder. Folders under `/Volumes` and other users' home folders are allowed by choice.
- **System paths allowed**: besides the exceptions listed above, `/usr`, `/opt`, `/cores`, `/Library` (the system one) and `/Applications` aren't refused by prefix. They are read only by default; with read & write the guest can write only what the user can write (the Virtualization process runs with the user's permissions), but `/opt/homebrew` or `/Applications`, for example, are writable by the user: sharing them with write access lets the guest change programs on the Mac.
- **VMs created before M3a**: the guest neither mounts `/mnt/nido` nor registers Rosetta by itself; the app, `nido share` and `nido rosetta enable` show the command to run once in the guest (it writes and enables a systemd unit, `nido-shares.service` or `nido-rosetta.service`; with `sudo`).
- **Saved state and snapshots in backups**: `state.vzvmsave` (the guest's memory) and the snapshots live in the bundle, under `~/Library/Application Support/Nido/VMs`, which Nido doesn't exclude from backups: Time Machine copies them (the state stays tied to this Mac's key, the disk doesn't). Anyone with access to the Mac as the same user can read them, like the disks.
- **Snapshot of a running VM**: it includes the guest's cache in the saved state, but not any writes that Virtualization.framework still holds internally (no API flushes them): in rare cases the snapshot's disk can lag slightly behind the saved state.
- **Syncing**: snapshot, restore and clone use `fsync`, not `F_FULLFSYNC`: after a power loss, the order of writes is less guaranteed than the protocol assumes (the drive may have kept data in its cache); recovery still refuses to proceed with leftover `.restore-*` files.
- **The guest's random number generator after a restore or a clone**: resuming the same saved state several times (a snapshot of a running VM, or of a suspended one) brings the guest back each time to the same state of its random number generator (Virtualization.framework offers no VM Generation ID through which the kernel would know); until the kernel mixes in new entropy (`virtio-rng` supplies it continuously), random values generated right after resuming (ephemeral keys, nonces, UUIDs) can repeat between two resumes. A clone inherits the source's `/var/lib/systemd/random-seed` (the kernel mixes in `virtio-rng` entropy at boot anyway). For long-lived secrets generated right after a resume, restart the VM.
- **Paths printed in the terminal**: paths and names read from `config.json` (`nido share list`, `nido start`'s "Warning:" messages, the builder's warnings) are printed with control characters made visible (`\u{…}`): a hand-edited `config.json` can't send escape sequences to the terminal.
- **The reason in `.suspend-result`**: the text is printed by `nido stop --suspend` as it is; only a process of the same user can write it (bundle `0700`).
- **Rosetta installation never run in automated tests**: it is covered only by tests with a stand-in; test it by hand before a release on a Mac without Rosetta.

## Residual risks (M3c)
- **The bridge's text leaves the Mac**: prompts and replies go through Hugging Face and the provider chosen by the router (or by the model's suffix), under their terms and with their logs. Nido warns about this the first time the bridge is turned on for a VM and doesn't keep them, but it can't guarantee what third parties do with them.
- **Less detailed router errors**: so that no account data reaches the guest, Hugging Face's `4xx`/`5xx` errors carry only the status code and a fixed text; a program in the guest no longer sees the precise reason for a `400`/`422` (for example, a parameter the model doesn't support).
- **`ThisDeviceOnly` not fully enforced**: Nido doesn't use the data protection keychain (that would need a keychain access group entitlement, and Nido ships only `com.apple.security.virtualization`), so the item lives in the login keychain, where `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` isn't guaranteed as it is in the data protection keychain: a copy of the login keychain could carry the token along. Another process of the same user can request the item (macOS asks for confirmation if it isn't the app that created it).
- **Slow requests**: a request that takes more than 10 s to arrive (e.g. a very slow or stuck guest client) gets a `408`; a stream cut halfway is logged as `502` and charged at the estimate.
- **Budget per VM, not per process**: every process in the guest can use the shim; a program in the guest can spend the VM's daily budget up to the limit (not beyond).
- **Guest shim**: since version 1.2.1, when the Mac closes the connection the shim also stops reading from the client, so a client that keeps its socket open (reused connections) no longer holds one of the 4 connections. A process in the guest can still hold them with requests in progress (for example long streams) and block the bridge **for that VM** (not for the others). The additional systemd restrictions apply only after Guest Tools 1.3.0 are installed in the VM.
- **Passwordless `sudo` for `nido`**: anyone with the user's SSH key (or a session on the console) is the VM's administrator. Restricting `sudo` to `nido-provision` alone would take the administration of their own VM away from the user; it remains a choice to revisit with the user (not changed in M3c).
- **First SSH connection**: the host key is accepted on first contact (`accept-new`); before that contact, another guest on the same NAT network presenting itself with the VM's address would be accepted (see M1). Afterwards, the key is tied to the VM even if the address changes.
- **The Mac memory warning**: Docker Desktop and other apps' VMs are counted by their current footprint (`phys_footprint`), not by their configured memory: with a Docker VM that grows after starting, the warning may come too late (an underestimate); if libproc can't read the open files of a Nido process, that VM can be counted twice (only extra warnings). The warning never blocks a start.
- **Panics in existing VMs**: without the explicit action, a VM created before M3c keeps invisible panics and no automatic restart.
- **`.cached` + `.full` disk**: measured without memory pressure on the Mac (round 3 of the integrity test under memory pressure wasn't run) and without a real power loss; `.full` remains the guarantee against losing writes already acknowledged to the guest.
- **Downloads in the guest**: Ollama is verified with the SHA-256 pinned in Nido (as trustworthy as the GitHub release of 2026-10-23); models with the digests of Ollama's registry; phase 1 packages with Debian's APT signatures.
- **Monitor not available with `nido start`**: the vsock device belongs to the process that runs the VM; for a VM started from Terminal, the panel says so (no new channel between processes).

## Residual risks (M3b)
- **IPSW without a Nido checksum**: the image is as trustworthy as the file the user chose and as Apple's check; between the inspection and the loading into Virtualization, a process of the same user could replace the file (Nido checks again shortly before, but can't close the window completely).
- **Canceling the installer**: goes through `progress.cancel()`. Tested once live with `VZMacOSInstaller` (IPSW 26.6.2, temporary root, at 9%): from the app (`MacInstallStore`) in 0.01 s, from `nido create --ipsw` with SIGINT in 0.03 s; in both cases no `.creating-*` folder and no bundle. If an installer ever stopped responding, on quit Nido waits at most 30 s (`MacInstallStore.quitCancelLimit`) and then quits anyway: the folder's lock is released with the process, and `sweepOrphanTombstones` removes it at the first listing of VMs (app or `nido list`) after 2 minutes. "Cancel…" from the card or the wizard instead waits without a limit, showing "Canceling…", without blocking the app.
- **macOS 27 beta not tested**: the message "it needs a Mac with macOS 27 or later" is covered by a fake loader, not by a real IPSW (the user's choice).
- **Identity left in macOS clones**: until the user runs the printed steps, the clone has the original's SSH host keys and computer name. Effects of the new identifier on the Keychain, iCloud or activation of an already configured machine: not verified.
- **"Type in VM" and the keyboard**: tested live on 2026-10-27 (macOS 26.6.2, German keyboard on the Mac and in the VM): the command arrives identical and `nido ssh` gets in. The command uses `"$HOME"` and no character that some keyboards produce only as a dead key (`~`, `^`, accents); with a different layout on the Mac and in the VM the text can arrive wrong (the panel's note says so). The mouse stays active while typing: a click in the guest can move the focus and send the text elsewhere (no Return is ever sent, so nothing is run by Nido).
- **First SSH connection**: as for Linux, the guest's host key is accepted on first contact (`accept-new`) and tied to the VM (`HostKeyAlias=nido-<id>`); the first `nido ssh` to a real macOS guest was run live on 2026-10-27 (`sshSucceeded` recorded).
- **`sshSucceeded` is a hint**: "ssh ended with a code other than 255" doesn't prove that authentication succeeded (a remote command can exit with other codes in any case). A clone doesn't inherit the flag (it needs a new host key, so the panel opens again). Its only effect is hiding the panel when the window opens.
- **SSH account with a key authorized by the user**: the public key is in `authorized_key.pub` (in Time Machine backups along with the bundle), and authorizing it in the guest is the user's own action.
- **Shared folders in macOS**: Nido's rules are the same as for Linux (read only by default), but the automatic mount at `/Volumes/My Shared Files` hasn't been verified in a configured guest; changing folders while the VM is running looks for the device by macOS's automatic mount tag.
- **Live features not tested**: resizing the window, closing and reopening it with the VM running, snapshots of a running VM from the app (covered by unit and session tests, not by UI tests).
- **Audio**: the guest's audio output plays through the Mac's speakers without a per-VM control; there is no microphone.
- **No clipboard**: copying between the Mac and the guest is manual (shared folders or `nido ssh`).

## Residual risks (M3d)
- **Shared CDN addresses**: an address learned for an allowed domain can also be reached under another name served by the same address. The SNI check (above) narrows this only for TCP 443 with the name in the first segment; other ports stay open (for example HTTP on 80), as do QUIC on UDP 443, ClientHellos without a name or with the name further in, and non-TLS data. This is why the base list contains only exact names and no general-purpose sites such as GitHub. Stated plainly: even with the base list alone, M3d doesn't contain a determined root guest (CDNs shared by many customers such as Fastly and Cloudflare, Host on port 80, a split ClientHello, QUIC, a learned address usable on every port for at least 10 minutes); it stops accidental and naive traffic.
- **`gvproxy` is third-party code**: Go with a TCP stack (gVisor) and its dependencies, which sees all the VM's allowed traffic and sends it out of the Mac as a user process. Mitigations: version and SHA-256 pinned in the repository, never downloaded at run time, signature, identifier and Team ID checked at every start (identifier only in an ad hoc build), control API never opened, Nido's filter in front of it, a token for the API on the gateway. A flaw in `gvproxy`'s handling of an allowed flow remains a risk; updates are an explicit choice. To a firewall on the Mac, the traffic belongs to `gvproxy`, not to Nido.
- **Orphaned `gvproxy` until the next start**: after a `kill -9` of Nido (or a crash), `gvproxy` stays alive, with that VM's SSH port on `127.0.0.1`, until another `start` (app or CLI) stops it. The VM died with the process, so the forward leads nowhere: what remains is a useless local port and one extra process.
- **CPU cost and speed**: `gvproxy` uses about 59% of one core at 12.75 MB/s (the line's limit), more than vmnet's 16–17%; the filter comes on top. For a VM that is always busy at full speed, that is one core fewer for everything else.
- **Suspended states from Nido 0.5.x**: the saved state (snapshots included) of a VM controlled with vmnet doesn't resume with 0.6.0's configuration ("the configuration changed"): it starts from scratch.
- **macOS base list and Apple ID**: with the base list, Setup Assistant gets to the desktop if the Apple ID is skipped, and `softwareupdate --list` works (verified live on 2026-11-03). Signing in with an Apple ID asks for other names (at least `appleid.apple.com`, `gsa.apple.com`, `gateway.icloud.com`), to be allowed by hand: not verified all the way through.
- **Allowed domains are channels**: a guest can send data to any service of an allowed domain (for example, upload files where the service allows it). With a wildcard (`*.example.com`) it can also get them out in the DNS questions for subdomains, which reach that zone's servers. Nido controls where traffic goes, not what it carries.
- **Tampering from the Mac** (out of scope, see above): a user process can widen `egress.json` or turn off `controlledNetwork` without Touch ID.
- **Re-allowing a recently removed domain** can take up to 60 s: the guest still uses the address in its cache, which the relay has forgotten. A domain never allowed before applies in about 3 s (negative TTL).
- **Ollama can move its files**: if the blobs move to a host other than the R2 bucket on the list, `ollama pull` fails until the list names the new host.
- **The relay's technical limits**: DNS responses larger than one frame don't pass (fragments are dropped, as is DNS over TCP to the gateway), so those names don't resolve; incoming ICMP (including path MTU messages) is dropped; the gateway's ARP is trusted as it is.
- **The relay runs in the VM's process**: a violated bounds check (`ByteView`) stops the whole process, that is `nido start` or the app with all its VMs. No frame passes unchecked, but the VM stops.
- **The log under attack**: a flood of all-different blocks for about 12 minutes can push the oldest blocks of `egress.log` out of the rotation (1 MiB plus one file). If the log can't be opened, the VM stays online with every block active: with `nido start` the blocks end up only on stderr; for a VM started from the app they are neither logged nor notified, and what remains is the warning in the VM window ("Network log unavailable…") and a notification (when there is a link or a non-regular file in place of the log).
- **Accepted edge cases**: SSH connections from the Mac left half-closed for more than 10 s are cut; after an SNI refusal, the same pair of addresses and ports is dropped silently for about 10 s, then further segments of the same connection form a new flow, whose first segment with data is checked again (non-TLS data passes, as above); a one-byte segment (such as a keepalive probe) before the ClientHello uses up the only read, and the name passes unchecked; a connection cut by removing a domain is remembered for 120 s (up to 16384 at a time) and each of its segments gets a reset, but afterwards, if its address is still allowed for another domain (same CDN), a segment of the old connection forms a new flow and passes (the SNI check sees data, not a ClientHello). The relay doesn't close the connection toward the server, which `gvproxy` keeps until it times out.
- **Real notifications not tested live**: the path through `UNUserNotificationCenter` (system permission, buttons in the notification) is covered by tests with a fake notifier; the real path has to be tested by hand. The same goes for the real Touch ID prompt (the tests use a fake authenticator).
- **The cost of watching**: the app rereads a VM's whole log when it changes (every 2 s at most); with large logs and many running VMs, this costs CPU.
- **macOS VMs with the base list alone**: activation, update catalogs and the clock work; Apple ID, iCloud and the App Store don't until the user allows their servers.
- **Ollama cache on the Mac**: archives of old versions stay in `~/Library/Caches/Nido/ollama` until they are deleted by hand; no free-space check before the download.

## Residual risks (audit 2026-11)
Source-only security audit of 2026-11-11 (commit `f955a94`). Fixed before 0.8.0: app crashes from numbers sent by the guest (monitor, Ollama status), quadratic parsing of chat responses, guest console processed in a single turn of the main actor, Sparkle feed replaceable from the preferences, release tag not tied to the verified commit. Still open:
- **A share inside a writable share**: `VZSharedDirectory` reopens the already validated folder by path (see the TOCTOU in M2). If a share sits inside another writable share, of the same VM or of another one, the guest can replace the inner folder with a link between validation and opening; the live update of shares repeats the window. Possible fix: refuse a share inside a writable share, or check `st_dev`/`st_ino` again after opening.
- **DHCP lease parser**: `DHCPLeases` also splits lines on CR, VT, FF and U+2028, not only on LF as `bootpd` does. A guest host name with these characters could create a fake block, but the effect doesn't go beyond client-id spoofing (M1): same attacker, same VM. It affects only VMs without the controlled network.
- **Failed AI bridge calls not counted**: a call that the router has already received but that times out (120 s), is canceled by the VM shutting down or gets a 4xx/5xx error costs 0 tokens against the daily limit. If Hugging Face bills those calls anyway, `tokensPerDay` doesn't cap all the spending. Accepted on 2026-11-12.
- **Spoofable SSH messages**: Nido classifies `ssh`'s exit 255 by reading stderr, which the guest controls; a guest can show a fake "host key changed". No boundary is crossed, only a wrong message.
- **Shared main actor**: console and chat are now read in chunks and in linear time, but all of the app's VMs use the same main actor; a guest can still slow down the interface within these limits.

## Out of scope
- Vulnerabilities in Virtualization.framework or the macOS kernel (to be reported to Apple).
- Security of the guest operating system after creation.
- An administrator user of the Mac (who can read everything anyway).
